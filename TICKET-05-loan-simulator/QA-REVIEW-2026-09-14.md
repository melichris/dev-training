## 4. Instructor Guidance: Why This Ticket Must Be Precise

A loan simulator is **different from the previous exercises**. A recipe list is either displayed or not. A loan payment can **look** correct and still be wrong by a few cents per month, or by thousands over 30 years. The ticket must therefore define **correctness numerically**, before any code is written.

### 4.1 Decisions the ticket must make explicitly

| Topic                | Question to answer in `TICKET.md`                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Loan type            | Fixed-rate amortising loan only? Interest-only? Variable rate out of scope?                                         |
| Formula              | Which formula? Write it down, e.g. `M = P · r / (1 − (1 + r)^−n)`                                                   |
| Rate conversion      | Is the input an **annual nominal** rate divided by 12, or an effective rate?                                        |
| Zero interest        | `r = 0` makes the formula divide by zero; the expected result is `P / n`                                            |
| Rounding             | Round each monthly payment to 2 decimals? How is the rounding difference handled in the final payment?              |
| Money representation | Floating-point or integer cents? (TICKET-03 raised this as an open point; resolve it here, where it really matters) |
| Input limits         | Min/max principal, rate, and duration; months or years; reject negative, zero, and non-numeric input                |
| Outputs              | Monthly payment? Total interest? Total cost? Full amortisation schedule table?                                      |
| Currency & locale    | Symbol, decimal separator, thousands separator                                                                      |

### 4.2 Reference values: acceptance criteria you can test

QA computed these with the standard fixed-rate formula. Use them (or your own, independently verified) as **test cases in the ticket**:

| Principal  | Annual Rate | Term       | Expected Monthly Payment |
| ---------- | ----------- | ---------- | ------------------------ |
| 10,000.00  | 5%          | 12 months  | **856.07**               |
| 10,000.00  | 0%          | 12 months  | **833.33**               |
| 200,000.00 | 6%          | 360 months | **1,199.10**             |

> Always cross-check reference values with an independent source, such as a spreadsheet `PMT()` function or a bank calculator, and cite that source in the ticket.

### 4.3 Suggested ticket skeleton

```text
# Ticket: Ticket-06-1 Loan Simulator (Fixed-Rate Amortisation) with Nuxt 4 + TypeScript

Type:     Training / Skill Development
Status:   Not Started

## Objective
Build a loan simulator that calculates the monthly payment, total interest and
amortisation schedule for a fixed-rate loan.

## Scope
- Input form: principal, annual rate, term (months)
- Pure calculation module (no Vue imports) in utils/ or composables/
- Results: monthly payment, total interest, total cost
- Amortisation table (month, payment, principal, interest, balance)

## Out of Scope
- Variable rates, fees, insurance, early repayment
- Persistence, authentication, backend

## Acceptance Criteria
- [ ] 10,000 @ 5% / 12 months → monthly payment 856.07
- [ ] 10,000 @ 0% / 12 months → monthly payment 833.33 (no division by zero)
- [ ] Final schedule balance is exactly 0.00
- [ ] Sum of principal portions equals the original principal
- [ ] Negative, zero, empty and non-numeric inputs are rejected with a message
- [ ] Results update reactively when any input changes
- [ ] Calculation logic is covered by unit tests (Vitest) using the values above

## Definition of Done
- [ ] All acceptance criteria verified with evidence
- [ ] npm run test: all passing (output attached)
- [ ] nuxt typecheck: zero errors (output attached)
- [ ] README and REPORT.md written
- [ ] Code reviewed and QA validated
```

### 4.4 Recommended approach order

1. **Pure function first:** `calculateMonthlyPayment(principal, annualRate, months)` with **no Vue or Nuxt code**.
2. **Unit tests** for that function, using the reference table, **before** building any UI. This is a perfect first exercise in test-driven development, because the expected outputs are already known.
3. **Schedule generator** plus tests (final balance = 0, principal sum = principal).
4. **Input form** with validation. Reuse the lessons from TICKET-03's validation defects: `Number()` + `Number.isFinite()`, not `parseFloat()`.
5. **Results and schedule UI.**
6. **Report** with test output as evidence.
