## 3. Findings

Severity scale: 🔴 **High** (blocks closure) · 🟠 **Medium** (must fix in this ticket) · 🟡 **Low** (should fix / learning point)

### 🔴 F-01: Amount validation accepts non-numeric and infinite values

**Where:** [ExpenseForm.vue:40-44](expense-tracker/src/components/ExpenseForm.vue#L40-L44), [ExpenseForm.vue:5](expense-tracker/src/components/ExpenseForm.vue#L5)

**Observation:** `parseFloat()` parses the **leading** numeric portion of a string and ignores the rest. `parseFloat('12abc')` returns `12`, so `isNaN()` never triggers. `parseFloat('Infinity')` returns `Infinity`, which is `> 0`.

**Contradiction with the report:** _Technical Decisions_ states:

> _"A truthy check alone would incorrectly accept non-numeric strings … Explicit numeric and range validation was required."_

The AC table also states _"validation tested for … non-numeric amount"_. It was tested with a **fully** non-numeric value (`abc`), not a **partially** numeric one, which is the edge case the ticket's own risk section asked you to cover.

**Reproduction:** Description `Lunch`, Amount `12abc` → **Add Expense** → row shows `$12.00`.

**Fix direction:**

```ts
const parsedAmount = Number(form.amount.trim()); // Number('12abc') → NaN
if (!Number.isFinite(parsedAmount) || parsedAmount <= 0) {
  /* error */
}
```

Also consider `<input type="number" min="0.01" step="0.01">` as a **first** layer, never the **only** layer.

**Why it matters (instructor note):** In a financial domain, validation defects become data-integrity defects. When you document a validation decision, list the **exact inputs you tested**, and the gaps become obvious.

### 🔴 F-02: The type-check evidence is invalid

**Where:** `REPORT.md` (_Evidence_, AC table, DoD table), `TICKET.md` DoD line 108

**Observation:** The root [tsconfig.json](expense-tracker/tsconfig.json) is `"files": []` with project `references`. `vue-tsc --noEmit` without `--build` does not follow references: it type-checks **zero files** and always exits 0. QA proved this by planting a type error (check #4 above).

**Good news:** The real code _does_ type-check: `npm run build` runs `vue-tsc --build` and passed.

**Fix:** Cite `npm run type-check` or `npm run build` output. Update the `TICKET.md` DoD wording so future tickets inherit the correct command.

**Why it matters (instructor note):** A check that cannot fail is not evidence. Break something once, confirm the check turns red, then trust it.

### 🟠 F-04: Provide/inject is inconsistently applied and inaccurately documented

**Where:** [useExpenses.ts:47](expense-tracker/src/composables/useExpenses.ts#L47), [TotalsDisplay.vue:3](expense-tracker/src/components/TotalsDisplay.vue#L3), [ExpenseRow.vue:24](expense-tracker/src/components/ExpenseRow.vue#L24)

**Observations:**

1. **Hardcoded currency.** `TotalsDisplay.vue` renders `Total: ${{ totalAmount }}` with a literal `$`. If the provided symbol changes to `€`, each row shows `€` but the total still shows `$`. The feature exists to give **one source of truth** for the symbol; this bypasses it.
2. **Location mismatch.** The report and AC table say `currencySymbol` is _"provided in `ExpenseTracker.vue`"_. It is actually provided inside `useExpenses()`. It works because the composable runs in `ExpenseTracker`'s setup, but the documentation is inaccurate.
3. **Design smell.** A data composable (`useExpenses`) now has a hidden UI side effect (`provide`). Anyone reusing `useExpenses()` elsewhere silently re-provides the currency. The ticket asked for provide _"from a top-level component"_.
4. **Untyped key.** The string key `'currencySymbol'` is unchecked, so a typo in either place fails silently to the `'$'` default.

**Fix direction:**

```ts
// src/keys.ts
export const CurrencySymbolKey: InjectionKey<string> = Symbol("currencySymbol");

// ExpenseTracker.vue
provide(CurrencySymbolKey, "$");

// ExpenseRow.vue AND TotalsDisplay.vue
const currencySymbol = inject(CurrencySymbolKey, "$");
```

## 7. Instructor Notes: Key Lessons

1. **Test the boundaries, not just the obvious failures.** `abc` is the easy case; `12abc`, `Infinity`, `0.001`, and `1e3` are where real bugs live. For every validation rule, write an input table before you code.
2. **`parseFloat` ≠ `Number`.** `parseFloat` is lenient (reads a prefix); `Number` is strict (whole string). Choose deliberately.
3. **A single source of truth only works if everyone uses it.** One hardcoded `$` defeats the purpose of `provide`/`inject`.
4. **Keep composables free of hidden UI side effects.** Data logic in the composable, wiring in the component.
5. **The report must describe the code as it _is_, not as it was intended.** Re-read the code while writing each claim.
