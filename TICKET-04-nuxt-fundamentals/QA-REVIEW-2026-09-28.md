### 🔴 F-14: The `/api/post/99` → 404 fix was not applied to `/api/products/:id`

**Where:** `server/api/products/[id].ts` still does `return products.find(...)` with no
existence guard, unlike `server/api/post/[id].ts:19-23` which now calls `createError(...)`.

**Reproduction:** `GET /api/products/99` (a nonexistent product id) → HTTP 204, empty body,
same defect the 2026-09-14 review reported for `/api/post/99`.

**Why this matters (instructor note):** When two endpoints share a bug because they share a
pattern, fixing one and not the other means the bug is still live — it will surface again the
next time someone calls the sibling route. Search for every place a pattern repeats before
declaring a bug class fixed.

---

### 🔴 F-15: Retroactive documentation describes and claims to test a route that does not exist

**Where:** `TICKET.md` and `REPORT.md`, multiple places — e.g. *"Post list fetched via
`useFetch('/api/posts')`"*, *"`server/api/posts.ts`"*, *"`server/api/posts/[id].ts`"*, and a
claim that these were "explicitly tested."

**Reality:** The actual, working files are `server/api/post/index.ts` and
`server/api/post/[id].ts` (singular). `GET /api/posts` returns 404 today — it is not a route
that exists. It cannot have been tested as described, because there was nothing to test.

**Why this matters more than a typo:** This ticket was written *specifically* in response to a
review that asked for honest, accurate, retroactive documentation instead of empty files. A
retroactive document that names files and routes that were never real repeats the exact
"report claims more than the code does" problem from 2026-09-14 (§6.2 of that review), now in
a brand-new document written to correct it.

**Fix direction:** Read the actual `server/api/` directory before writing (or re-writing)
`TICKET.md`/`REPORT.md`, and name only files and routes that exist. If the route was renamed
at some point (`posts` → `post`), say so explicitly instead of leaving stale names in place.

### 🟠 F-16: The page-level 404 — the actual point of the original finding — is still not real

**Where:** `pages/posts/[id].vue`.

**Observation:** The page destructures an `error` ref from `useFetch` and shows a
`v-else-if="error"` branch with text "Post not found." But it never calls
`throw createError({ statusCode: 404, fatal: true })`. `GET /posts/99` therefore returns
**HTTP 200** with an error *message* in the body, not an HTTP 404. Search engines, monitoring,
and any client checking the status code would see a successful response for a page that
doesn't exist.

**Why this is the real finding, not the API fix:** The 2026-09-14 review's reproduction case
was about HTTP semantics, not about whether text appears on screen. The API layer is now
correct; the page layer, which a real user or crawler actually hits, is not.

**Fix direction:**
```ts
if (error.value) {
  throw createError({ statusCode: 404, statusMessage: 'Post not found', fatal: true })
}
```
