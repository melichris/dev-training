### 🔴 F-02: API returns `204 No Content` for missing resources

**Where:** [server/api/post/[id].ts:10-12](nuxt-fundamentals/server/api/post/[id].ts#L10-L12), [server/api/products/[id].ts:28-30](nuxt-fundamentals/server/api/products/[id].ts#L28-L30)

**Observation:** `posts.find(...)` returns `undefined` for unknown IDs, and the handler returns it directly. The server framework (h3) turns `undefined` into **HTTP 204 No Content**, which means "success, nothing to send". QA confirmed `GET /api/post/99` → `204`.

**Impact:**

- API clients cannot tell "not found" apart from "success".
- The page `/posts/99` returns **HTTP 200** containing "Post not found." Search engines would index it as a real page (a _soft 404_).
- The detail pages never destructure `error`, so real failures (e.g. a 500) are also displayed as "not found".

**Fix direction:**

```ts
// server
const id = Number(getRouterParam(event, "id"));
if (!Number.isInteger(id))
  throw createError({ statusCode: 400, statusMessage: "Invalid id" });
const post = posts.find((p) => p.id === id);
if (!post)
  throw createError({ statusCode: 404, statusMessage: "Post not found" });
return post;
```

```ts
// page
const { data: post, error } = await useFetch(`/api/post/${route.params.id}`);
if (error.value)
  throw createError({ statusCode: error.value.statusCode, fatal: true });
```

### 🟠 F-03: Loading states that can never be seen

**Where:** [posts/[id].vue:4](nuxt-fundamentals/app/pages/posts/[id].vue#L4) & [:8](nuxt-fundamentals/app/pages/posts/[id].vue#L8), [posts/index.vue:7](nuxt-fundamentals/app/pages/posts/index.vue#L7) & [:12](nuxt-fundamentals/app/pages/posts/index.vue#L12), [products/[id].vue:4](nuxt-fundamentals/app/pages/products/[id].vue#L4) & [:8](nuxt-fundamentals/app/pages/products/[id].vue#L8), [products/index.vue:16](nuxt-fundamentals/app/pages/products/index.vue#L16)

**Observation:** Every page uses `await useFetch(...)`. With `await`, Nuxt **waits for the data before rendering**, both on the server during SSR, and before completing client-side navigation. The `v-if="status === 'pending'"` "Loading…" branches are therefore effectively unreachable.

**Instructor tie-in:** Your own [docs/nuxt-dataFetching.md:3](docs/nuxt-dataFetching.md#L3) lists _"difference between await and lazy"_ as a topic to study. This is that exact concept showing up in your code. `useLazyFetch` (or `useFetch(..., { lazy: true })`) renders immediately and **does** show the pending state. Completing that doc section, with a before/after demo in this project, would be an excellent deliverable.

## 6. Instructor Notes: Key Lessons

1. **An empty ticket is not a ticket.** The process exists to create **shared criteria for "done"**, not to create files. Fill it in before the first line of code.
2. **HTTP status codes are part of your API contract.** `200` / `204` / `400` / `404` mean different things to browsers, clients, and search engines.
3. **`await useFetch` blocks; `useLazyFetch` does not.** Loading UI only makes sense with the lazy variant, and this is already on your study list.
4. **One package manager per project.** Two lockfiles mean two possible dependency trees.
5. **Finish before you start.** Opening Loan-Simulator and TICKET-05 while TICKET-04 had no report multiplies unfinished work. Limit work-in-progress to **one open ticket** until it is closed.
