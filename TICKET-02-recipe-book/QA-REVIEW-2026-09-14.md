## 3. Findings

Severity scale: 🔴 **High** (blocks closure) · 🟠 **Medium** (must fix in this ticket) · 🟡 **Low** (should fix / learning point)

### 🔴 F-01: Validation allows a recipe with zero ingredients

**Where:** [RecipeForm.vue:28-31](recipe-book/src/components/RecipeForm.vue#L28-L31) and [RecipeForm.vue:44](recipe-book/src/components/RecipeForm.vue#L44)

**Observation:** Validation checks the _raw string_ (`form.ingredients.trim()`), but the stored value is the _parsed array_ (`split(',') → trim → filter`). They are not the same thing.

**Reproduction:**

1. Enter name `Soup`.
2. Enter ingredients `,` (or `, ,`).
3. Click **Add Recipe**.

**Expected:** Error "At least one ingredient is required." This is exactly what `APPROACH.md` step 4 promised (_"`ingredients` has at least one entry"_).
**Actual:** Recipe is added with `ingredients: []` and renders `Ingredients: N/A`.

**Why it matters (instructor note):** Always validate the **value you are about to store**, not the raw input you received. Parse first, then validate the parsed result.

**Fix direction:**

```ts
const parsedIngredients = form.ingredients
  .split(",")
  .map((i) => i.trim())
  .filter(Boolean);
if (parsedIngredients.length === 0) {
  /* error */
}
```

### 🔴 F-02: The type-check evidence is invalid

**Where:** `REPORT.md` sections _How It Was Done_, _Evidence_, _Acceptance Criteria_, _Definition of Done_

**Observation:** The report states ` vue-tsc --build` ran "with zero errors" as proof of type correctness. The root [tsconfig.json](recipe-book/tsconfig.json) contains `"files": []` plus project `references`. Without `--build`, `vue-tsc` does **not** follow references: it checks **nothing** and always exits 0.

**QA proof:** A deliberately broken component (`const x: number = "not a number"`) was added to a copy of the sibling TICKET-03 project, which uses the identical config. ` vue-tsc --build` still exited **0**. ` vue-tsc --build -p tsconfig.app.json` correctly failed with `TS2322`.

**Good news:** The code _does_ type-check: `npm run build` runs `vue-tsc --build`, which passed. The code is fine; the **evidence** is not.

**Why it matters (instructor note):** Evidence only counts if it would have **failed when the code was wrong**. Before citing a command as proof, break something on purpose and confirm the command catches it.

**Fix:** Cite `npm run type-check` (or `npm run build`) and paste its real output.

### 🟠 F-04: Mock data cannot demonstrate "sort by creation date"

**Where:** [types.ts:17](recipe-book/src/types/types.ts#L17), [types.ts:24](recipe-book/src/types/types.ts#L24), [types.ts:31](recipe-book/src/types/types.ts#L31), [types.ts:38](recipe-book/src/types/types.ts#L38)

**Observation:** Every mock recipe uses `createdAt: Date.now()`, evaluated at the same instant on module load → **one identical timestamp** for all four. Sorting by date therefore produces no visible change on the initial data. In addition, the names `Recipe 1…4` are already alphabetical, so "sort by name" also shows no visible change.

**Impact:** Acceptance criterion _"Recipes can be sorted by multiple criteria"_ is marked ✅, but two of the three sort modes **cannot be observed** with the shipped data. A QA engineer cannot validate what the data cannot show.

**Why it matters (instructor note):** Test data is part of the deliverable. Design fixtures that **prove** each feature: distinct fixed dates (e.g. `new Date('2026-08-01').getTime()`), names out of alphabetical order, mixed vegetarian flags.

## 7. Instructor Notes: Key Lessons

1. **Evidence must be falsifiable.** If a check cannot fail, it proves nothing. Break the code on purpose once, and confirm the check catches it.
2. **Validate the stored shape, not the raw input.** Parse → validate → store.
3. **Test data is a test.** Fixtures must be designed so every acceptance criterion is _visibly_ demonstrable.
4. **The report is a deliverable, not a formality.** Proofread commands and file names, because a reviewer will copy-paste them.
5. **"Done" means another person can verify it without asking you.** Broken links and missing screenshots mean the reviewer has to ask.
